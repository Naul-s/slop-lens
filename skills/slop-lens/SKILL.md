# SlopLens — "왜 AI 슬롭으로 느껴지나" 판독 스킬

**원칙: 슬롭인지 아닌지는 사람이 가장 잘 판단한다.** 이 스킬의 일은 점수를 맞히는 것이 아니라,
사람이 그렇게 느끼는 **원인을 정확히 짚고**(무엇이 보이고 들리는가), **왜 그렇게 느껴지는지 설명하고**, **해결책을 주는 것**이다.
코드 패턴은 원인을 설명하는 보조 근거일 뿐이다. 화면·소리가 공들여 보이면 코드 신호보다 그 판단이 우선한다.

## 워크플로

### 0. (Unity 게임만) 실행 캡처
Unity 프로젝트는 코드만으로는 화면·소리를 알 수 없다. 먼저 실행 캡처를 만든다 (원본은 건드리지 않음 — 복사본에서 빌드):
```bash
python {{SLOP_LENS_HOME}}/bin/slop-lens.py unity-capture "<Unity 프로젝트 경로>" --seconds 30
```
- 첫 실행은 에셋 임포트로 10~30분, 이후는 몇 분. 끝나면 게임 창이 약 30초 뜨고 자동 플레이한다(소리는 스피커 음소거, 키 입력은 게임 창이 맨 앞일 때만).
- 사용자에게 실행 전에 이 사실(시간, 창이 뜸)을 알린다.
- Unity MCP 서버(예: CoplayDev unity-mcp)가 연결돼 있다면 에디터에서 플레이 모드 진입 → 스크린샷 → 콘솔 로그를 직접 수집해도 된다.

### 1. 검사
MCP: `slop_scan` { target, kind: "auto" }  ·  CLI: `slop-lens.py scan <대상>`
- 웹/웹게임은 실제 브라우저로 렌더·클릭·플레이(Node 렌더 프로브 필요), 사운드를 녹음해 분석한다.
- 에셋(아이콘·스프라이트·효과음·음악)을 분석하고 **리뷰용 시트 이미지**(화면 시트, 에셋 시트)를 만든다.
- 결과는 **잠정**이다. 2단계 리뷰를 해야 확정된다.

### 2. 지각 리뷰 (판정의 핵심)
MCP: `slop_review_protocol` { scan_id, blind: true }  ·  CLI: `scan <대상> --protocol --blind`

**먼저 블라인드로 본다.** 측정 결과를 보고 나서 화면을 보면 측정에 끌려간다. `blind: true`로 받은 자료로 화면만 보고 답한 뒤 제출하고,
필요하면 `blind` 없이 다시 열어 측정과 비교한다. 제출할 때 `meta`에 `blind`(측정을 안 보고 리뷰했나)와 `knew_expected`(제작자·사용자의 판단을 미리 알았나)를 정직하게 적는다 — 리포트 신뢰도에 반영된다.

**게임은 리뷰 없이 판정하지 않는다.** 검증에서 게임 측정 점수는 AI 제작물과 사람 제작물을 가르지 못했다(AUC 0.48). 리뷰가 없으면 리포트는 "판정 보류"로 나오고, 그 점수는 마감 결함의 양일 뿐이라고 사용자에게 설명한다.
1. 시트(썸네일 모음)로 전체 흐름을 본 뒤, 프로토콜의 **"원본 확인 목록"에 있는 프레임과 스크린샷 조각을 한 장씩 원본 크기로 연다.**
   작은 글자·빈칸(`—`)·순색 UI·겹친 문구·잘린 레이아웃은 시트에서는 보이지 않는다. 각 장마다 실제로 보이는 것을 `frames` 메모로 남긴다.
2. 프로토콜의 **화면 문구 목록**을 프레임과 대조한다: 쓸데없는 안내문, 화살표+글자 중복, 영어 대문자 장식 라벨, 개발용·빈칸 문구, 어디에나 붙는 태그라인.
3. 사운드 측정 요약을 읽는다 (오실레이터 단음인지, 효과음이 있는지, 플레이 중 무음 비율).
4. 감각별로 답한다 — 레벨 0(공들인 결과물)~4(명백한 슬롭), **근거(어느 프레임의 어디)**, **왜 사람이 그렇게 느끼는지**, **해결책**:
   S1 첫인상 · S2 시각 정체성 · S3 에셋 품질·일관성 · S4 UI·타이포 기본값 · S5 사운드 · S6 움직임·피드백 · S7 카피 · S8 실체·동작 · S9 AI 생성 이미지 처리(생성기 출력 그대로 vs 화풍·팔레트·조명을 맞춰 다듬음) · C1 공들인 흔적(반대 증거)
5. 제출: `slop_submit_review` { scan_id, review, frames, meta: {reviewer, blind, knew_expected} }  ·  CLI: `scan <대상> --review review.json`

리뷰 요령
- 측정이 문제를 가리켜도 화면이 실제로 공들여 보이면 낮은 레벨을 준다 (예: Stripe의 보라 그라디언트는 브랜드 고유의 리본 형태 → 0).
- 측정이 조용해도 보이는 문제가 있으면 높은 레벨을 준다 (예: 단색 바닥 위 순색 HP 막대).
- 지연 로딩 때문에 빈 카드로 찍힌 웹 조각은 사이트 결함이 아니라 캡처 한계로 적는다.
- 자동 플레이의 한계(곡 선택 실패 등)로 생긴 화면은 게임 결함과 구분해 적는다. 보지 못한 항목은 `na`.
- 사용자가 이미 판단을 밝혔다면 그 사실을 리포트에 밝힌다 (독립 판정이 아님).

### 3. 설명 (사용자에게)
리포트의 **"왜 AI 슬롭으로 느껴지나"** 섹션 순서대로:
1. 판정(확정/잠정), Slop Index, 유형(AI 지문 × 완성도 결함)
2. 원인 상위 3~5개 — 각각 **느낌 → 보이고 들리는 근거 → 측정 근거 → 해결**
3. 공들인 흔적(반대 증거)
점수만 던지지 말고, 그 결과물의 구체적 화면·소리·파일을 가리키며 설명한다.

### 4. 해결
`slop_fix_plan` { scan_id } → 빠른 수정 → 핵심 개선 → 깊은 리디자인 + Anti-Slop 브리프.
수정 후 다시 검사·리뷰해서 전후를 비교한다.

## 수정할 때 반드시 지킬 것
- 가짜를 더 그럴듯한 가짜로 바꾸지 않는다 (후기·통계·연락처). 없으면 삭제하거나 묻는다.
- 브랜드·아트 방향 결정(팔레트, 폰트, 시그니처, 사운드 질감)은 사용자에게 먼저 묻는다.
- 검사기만 통과하게 숨기지 않는다. 목표는 사람이 받는 인상이다.
