# SlopLens 판정 기준 (Criteria)

> 이 문서는 `scripts/gen_criteria.py`가 규칙 레지스트리에서 자동 생성합니다. 직접 수정하지 마세요.

## 1. 정의

**AI Slop**은 "AI가 만들었다"는 사실 자체가 아니다. **생성 모델의 기본값을 사람의 결정 없이 그대로 내보내서**,
보는 사람이 "대충 자동으로 찍어냈다"고 즉시 느끼는 결과물이다. AI로 만들었어도 사람이 방향을 정하고 다듬었다면 슬롭이 아니고,
사람이 만들었어도 템플릿 기본값과 가짜 완성도로 채웠다면 슬롭처럼 느껴진다.

따라서 SlopLens는 "AI가 썼는가?"를 맞히는 탐지기가 아니라, **사람이 슬롭이라고 느끼는 원인을 측정하고 고치게 하는 도구**다.

## 2. 두 축 모델

| 축 | 질문 | 대표 신호 |
|---|---|---|
| **AI 지문 (Genericness)** | 수천 개의 AI 결과물과 구별되는가? | 보라 그라디언트, Inter 단독, 정형 랜딩 골격, 상투어, 이모지 아이콘, 블러 블롭 |
| **완성도 결함 (Effort deficit)** | 보이는 것만큼 실제로 완성돼 있는가? | 죽은 링크, 가짜 후기·통계, alert 폼, 더미 텍스트, 게임필·사운드 없음 |

| | 완성도 결함 낮음 | 완성도 결함 높음 |
|---|---|---|
| **AI 지문 높음** | 세련된 템플릿 — 잘 돌아가지만 어디서 본 듯함 | **전형적 AI 슬롭** |
| **AI 지문 낮음** | 의도된 결과물 | 덜 만든 결과물 — 마무리가 비어 있음 |

## 3. 지각 요인 5가지 — 사람은 *왜* 슬롭이라고 느끼나

모든 규칙은 아래 요인 중 하나 이상에 연결된다. 리포트는 요인별 점수도 보여준다.

| 요인 | 이름 | 설명 |
|---|---|---|
| P1 | 평균 회귀 (Sameness) | 어디서 본 듯한 기본값의 조합. 수천 개의 AI 결과물과 구별되지 않는다. |
| P2 | 의도 부재 (No intent) | 이 제품·게임만의 구체적 결정이 보이지 않는다. 누구를 위해, 왜 이렇게 만들었는지 없음. |
| P3 | 껍데기 완성도 (Hollow polish) | 겉보기엔 완성품인데 눌러보면 동작하지 않거나 가짜다 (죽은 링크, 가짜 후기, alert). |
| P4 | 언캐니 아티팩트 (Uncanny artifacts) | 생성 모델 특유의 흔적: 뭉개진 글자·손, 플라스틱 질감, 생성기 메타데이터. |
| P5 | 비일관성 (Incoherence) | 스타일·톤·규칙이 섞여 하나의 사람이 결정한 결과물로 보이지 않는다. |

## 4. 판정 규칙 (정적 분석 + 렌더 실측)

- **정적** 규칙은 소스·에셋만으로 항상 실행된다 (Python만 있으면 됨).
- **실측(RND-)** 규칙은 Node 렌더 프로브가 설치돼 있을 때 실제 브라우저로 렌더링·클릭·플레이한 결과로 판정한다. `대체` 열의 정적 규칙은 실측이 있으면 버려진다 — 실측이 문제를 찾으면 실측 결과로, 문제가 없으면 정적 추정의 오탐이 제거된다 (`clean_supersedes=False`인 규칙은 실측에서 재현되지 않아도 정적 증거를 유지).

#### VIS-01 AI 기본 그라디언트 (인디고→보라→핑크)

**왜 슬롭으로 느끼나** — indigo-500→purple-600 계열 그라디언트는 LLM이 '모던한 느낌'을 요청받았을 때 가장 먼저 꺼내는 기본값이다. 사람들은 이 색 조합을 수많은 AI 생성 SaaS 페이지에서 반복해 봤기 때문에 보자마자 '자동 생성'으로 분류한다.

**해결** — 브랜드 고유 1차색 1개 + 중성색 스케일로 팔레트를 다시 정의하고, 그라디언트는 꼭 필요한 1곳에만 쓴다.

1. 브랜드 성격을 형용사 3개로 정하고 그에 맞는 1차색을 고른다 (보라/남색 계열은 의도가 있을 때만).
2. CSS 변수/Tailwind theme에 --brand, --ink, --paper, --muted 토큰을 정의한다.
3. 배경 그라디언트는 단색 + 질감(노이즈, 사진, 패턴)으로 대체한다.
4. 강조는 색이 아니라 크기·굵기·여백 대비로 만든다.

```
:root{--brand:#e4572e;--ink:#1d1a16;--paper:#f6f1e7;--muted:#8a8172}
.hero{background:var(--paper);color:var(--ink)}
.btn{background:var(--brand)}
```

> 에이전트 지시문: indigo/violet/purple/pink 그라디언트를 쓰지 말 것. 브랜드 1차색 1개와 따뜻하거나 차가운 중성색 스케일로만 구성할 것.

#### VIS-02 그라디언트 텍스트 (bg-clip-text)

**왜 슬롭으로 느끼나** — 헤드라인 일부에 그라디언트를 입히는 기법은 2023년 이후 AI 랜딩 페이지의 상징이 되었다. 의미 없이 '강조된 단어'는 오히려 읽기를 방해한다.

**해결** — 그라디언트 텍스트를 제거하고 단색 + 서체 대비(굵기/이탤릭/세리프 전환)로 강조한다.

1. bg-clip-text/text-transparent 조합을 제거한다.
2. 강조 단어는 같은 색에서 굵기나 서체(예: 세리프 이탤릭)를 바꿔 표현한다.
3. 정말 필요하면 1페이지 1회, 브랜드 색 단색 밑줄/하이라이트로 대체한다.

```
<h1>매일 쓰는 <em class="accent">가계부</em></h1>
.accent{font-family:'Fraunces',serif;font-style:italic;color:var(--brand)}
```

> 에이전트 지시문: 그라디언트 텍스트(bg-clip-text, text-transparent) 금지. 강조는 굵기·서체·크기 대비로만.

#### VIS-03 글래스모피즘 남용 (backdrop-blur)

**왜 슬롭으로 느끼나** — 반투명 흰색 + 블러 카드는 깊이를 연출하려는 AI의 기본 해법이다. 여러 곳에 반복되면 정보 위계가 흐려지고 '템플릿' 인상이 강해진다.

**해결** — 블러는 실제 겹침이 있는 곳(고정 내비 등) 1곳에만 남기고 카드는 불투명 면 + 얇은 보더로 바꾼다.

1. backdrop-blur 사용처를 목록화하고 실제로 뒤에 콘텐츠가 겹치는 곳만 남긴다.
2. 카드는 bg-[--paper] + 1px 보더 또는 그림자 없이 여백으로 구분한다.

```
.card{background:var(--paper);border:1px solid color-mix(in srgb,var(--ink) 12%,transparent)}
```

> 에이전트 지시문: 글래스모피즘(backdrop-blur 반투명 카드) 사용 금지, 고정 헤더 1곳만 예외.

#### VIS-04 Tailwind 기본 팔레트만 사용 (브랜드 토큰 없음)

**왜 슬롭으로 느끼나** — indigo/slate/gray 기본 스케일을 그대로 쓰면 수만 개의 Tailwind 결과물과 같은 색 공간에 놓인다. 브랜드 토큰이 없다는 것은 '색을 결정한 사람이 없다'는 신호다.

**해결** — tailwind theme(또는 @theme)에 브랜드 토큰을 정의하고 기본 팔레트 직접 참조를 토큰으로 치환한다.

1. tailwind.config / @theme 에 brand, ink, paper, muted, accent 토큰을 만든다.
2. bg-indigo-600 → bg-brand, text-gray-600 → text-muted 식으로 일괄 치환한다.
3. 회색은 순수 회색 대신 브랜드 색조가 섞인 warm/cool gray로 정의한다.

```
@theme {
  --color-brand: oklch(62% 0.19 35);
  --color-ink: oklch(22% 0.02 60);
  --color-paper: oklch(97% 0.01 80);
}
```

> 에이전트 지시문: Tailwind 기본 색(indigo/violet/slate/gray-xxx) 직접 사용 금지. 프로젝트 고유 디자인 토큰을 먼저 정의하고 그것만 사용.

#### VIS-05 기본 서체 단일 사용 (Inter/Poppins/시스템)

**왜 슬롭으로 느끼나** — Inter·Poppins·시스템 산세리프 한 종만 쓰면 타이포그래피에서 개성이 사라진다. 사람은 글자 모양에서 브랜드 목소리를 가장 먼저 느끼는데, 그 목소리가 '기본값'이다.

**해결** — 디스플레이 서체 1종 + 본문 서체 1종으로 페어링하고 크기·굵기·자간 스케일을 정의한다.

1. 헤드라인용 개성 있는 서체(세리프, 그로테스크, 손글씨 등)를 브랜드 성격에 맞춰 고른다.
2. 본문은 가독성 좋은 서체를 유지하되 한글은 Pretendard/본고딕/마루부리 등에서 의도적으로 선택한다.
3. 타입 스케일(예: 1.25배)과 헤드라인 자간(-0.02em 등)을 토큰화한다.

```
:root{--font-display:'Fraunces',serif;--font-body:'Pretendard',sans-serif}
h1,h2{font-family:var(--font-display);letter-spacing:-0.02em}
```

> 에이전트 지시문: Inter/Poppins 단독 사용 금지. 브랜드 성격을 드러내는 디스플레이 서체와 본문 서체를 페어링할 것.

#### VIS-06 모든 요소에 같은 큰 라운드 (rounded-2xl 일괄)

**왜 슬롭으로 느끼나** — 카드·버튼·이미지·입력창이 전부 같은 rounded-xl/2xl이면 '말랑한 기본 UI 키트' 인상이 된다. 사람이 설계한 UI는 요소의 역할마다 모서리 규칙이 다르다.

**해결** — 모서리 반경을 역할별 2~3단계 토큰으로 나누고, 일부 요소는 각지게 둔다.

1. --radius-s(4px) / --radius-m(10px) / --radius-pill 로 역할 기반 규칙을 정한다.
2. 큰 이미지·섹션 컨테이너는 0 또는 작은 반경으로 바꿔 긴장감을 만든다.

```
:root{--r-s:4px;--r-m:10px}
.card{border-radius:var(--r-s)} .chip{border-radius:999px}
```

> 에이전트 지시문: rounded-2xl 일괄 적용 금지. 역할별로 다른 모서리 반경 규칙(작게/각지게 포함)을 쓸 것.

#### VIS-07 그림자 남발 (shadow-lg/xl 반복)

**왜 슬롭으로 느끼나** — 모든 카드가 떠 있으면 아무것도 떠 있지 않은 것과 같다. 큰 그림자의 반복은 깊이 체계가 설계되지 않았다는 신호다.

**해결** — 고도(elevation) 단계를 2개로 줄이고 대부분의 면은 그림자 없이 보더/여백으로 구분한다.

1. shadow-lg/xl/2xl을 전부 찾아 '정말 떠 있어야 하는 요소'(모달, 드롭다운)만 남긴다.
2. 카드 구분은 배경 명도 차이 또는 1px 보더로 대체한다.

```
:root{--elev-1:0 1px 2px rgb(0 0 0/.06);--elev-2:0 8px 24px rgb(0 0 0/.12)}
```

> 에이전트 지시문: shadow-lg/xl 반복 금지. 고도는 최대 2단계, 대부분은 그림자 없이.

#### VIS-12 토큰 없는 하드코딩 색상 난립

```

```

#### RND-01 AI 기본 그라디언트 (렌더 색상환 실측)

**왜 슬롭으로 느끼나** — 실제로 화면에 칠해진 그라디언트의 색상(hue)이 남색→보라→핑크(200°~340°) 구간에 걸쳐 있다. hex 목록이 아니라 렌더링된 색을 재므로 Tailwind 클래스, CSS 변수, 인라인 스타일 어느 방식으로 만들었든 잡힌다. 사람들이 'AI SaaS 색'으로 인식하는 바로 그 색 범위다.

**해결** — 브랜드 1차색 1개 + 중성색 스케일로 다시 정의하고, 그라디언트는 꼭 필요한 1곳에만 쓴다.

1. 리포트의 선택자 위치에서 그라디언트를 단색·질감·사진으로 바꾼다.
2. 넓은 면적(섹션 배경)부터 우선 제거한다.
3. 색 토큰을 정의하고 남색~보라 계열은 의도가 있을 때만 쓴다.

```
:root{--brand:#e4572e;--paper:#f6f1e7;--ink:#1d1a16}
.cta{background:var(--ink);color:var(--paper)}
```

> 에이전트 지시문: 남색~보라~핑크(색상환 200°~340°) 그라디언트 금지. 브랜드 1차색 + 중성색으로만.

#### RND-02 그라디언트 텍스트 (실측)


> 에이전트 지시문: 그라디언트 텍스트 금지.

#### RND-03 렌더된 서체 단조로움 (실제 적용 폰트)

#### COL-01 AI 상투 배색 (화면 전체 색 구성)

**왜 슬롭으로 느끼나** — 화면 대부분을 차지하는 색 구성이 AI 생성물에서 반복적으로 보이는 배색(보라 테크, 어두운 청록 시네마틱, 파스텔 하늘, 네온 사이버, 크림 코지)과 일치한다. 사람들은 개별 요소보다 먼저 전체 색으로 첫인상을 정하기 때문에, 배색이 평균값이면 내용을 보기 전에 '어디서 본 것'으로 분류한다.

**해결** — 작품의 장면·소재·브랜드에서 팔레트를 도출한다(배경 1, 중성 2, 강조 1). 강조색은 다른 작품과 겹치지 않게 고른다.

1. 작품을 대표하는 실제 장면/사진 1장을 정한다.
2. 그 장면에서 5~6색을 추출해 팔레트로 만든다(Coolors, Adobe Color).
3. 배경을 단색 평면 대신 그 팔레트의 질감·그라데이션으로 채운다.
4. 강조색은 핵심 행동 1~2곳에만 쓴다.

> 에이전트 지시문: 보라 테크·어두운 청록·파스텔 하늘·네온 사이버·크림 코지 같은 평균 배색 금지. 작품의 장면에서 팔레트를 도출할 것.

#### COL-02 빈 단색 화면 (환경·배경 아트 부재)

**왜 슬롭으로 느끼나** — 플레이 화면의 대부분이 한 가지 색 평면이다(단색 잔디, 하늘색 바탕). 공간·장소를 보여주는 환경 아트가 없어서 '테스트 씬'처럼 비어 보이고, 캐릭터와 오브젝트가 어디에 있는지 감정이 생기지 않는다.

**해결** — 바닥 타일셋·소품·조명·원경으로 공간을 채운다. 평면을 유지한다면 질감·명암 변화와 경계를 준다.

1. 플레이 공간의 장소를 정한다(숲 가장자리, 마을 마당 등).
2. 바닥 타일 변형 3~4종과 소품 5~10종을 배치한다.
3. 원경·그림자·조명으로 깊이를 만든다.

#### LAY-01 정형화된 랜딩 페이지 골격

**왜 슬롭으로 느끼나** — Hero → 기능 3개 → 사용 방법 3단계 → 후기 → 요금제 3단 → FAQ → CTA → 푸터. LLM은 '랜딩 페이지'를 이 순서로 거의 고정 생성한다. 사람은 내용을 읽기도 전에 스크롤 리듬만으로 '또 이 구조'라고 느낀다.

**해결** — 섹션을 '사용자가 결정에 필요한 질문' 순서로 재구성하고, 해당 제품에만 있는 섹션을 1개 이상 만든다.

1. 방문자가 이 페이지에서 답을 얻어야 할 질문 3~5개를 적는다 (예: '내 은행도 되나?').
2. 각 질문에 답하는 섹션만 남기고 관성적으로 넣은 섹션(How it works, Stats, FAQ 등)은 삭제·병합한다.
3. 제품 고유 섹션(실제 데모, 비교표, 제작 과정, 창업자 노트 등)을 추가한다.
4. 섹션마다 레이아웃 형태(전폭 이미지/2열/리스트/표)를 다르게 한다.

```
Hero(실제 화면) → '이런 분께 맞아요/안 맞아요' → 라이브 데모 → 실제 고객 1명 케이스 스터디 → 가격(1개 플랜+FAQ 통합) → 창업자 노트
```

> 에이전트 지시문: Hero→Features→How it works→Testimonials→Pricing→FAQ→CTA 정형 순서 금지. 방문자의 실제 질문 순서로 섹션을 구성하고, 이 제품에만 있는 섹션을 포함할 것.

#### LAY-02 3열 동일 카드 그리드 반복

**왜 슬롭으로 느끼나** — 기능·후기·요금제가 모두 '같은 크기 카드 3개'로 배열되면 페이지 전체가 하나의 패턴 반복으로 읽힌다. 위계(무엇이 가장 중요한가)가 사라진다.

**해결** — 그리드마다 위계를 준다: 1개 크게 + 나머지 작게, 비대칭 2열, 리스트, 표 등으로 형태를 바꾼다.

1. 3열 그리드를 전부 찾고 섹션별로 '가장 중요한 1개'를 정한다.
2. 그 1개는 span-2 또는 전폭으로 키우고 나머지는 보조 리스트로 만든다.

```
.features{display:grid;grid-template-columns:2fr 1fr;gap:var(--space-6)}
.features .lead{grid-row:span 2}
```

> 에이전트 지시문: 동일 크기 카드 3열 그리드를 섹션마다 반복하지 말 것. 섹션마다 레이아웃 형태와 위계를 다르게.

#### LAY-03 'Most Popular' 가운데 강조 요금제

**해결** — 실제 가격 정책이 없다면 요금제 섹션을 빼고, 있다면 실제 차이(한도·지원 범위)를 표로 명확히 비교한다.

1. 가격이 정해지지 않았다면 '베타 무료 · 정식 출시 시 안내' 한 줄로 대체한다.
2. 가격이 있다면 플랜 수를 줄이고 차이를 비교표로 보여준다.

```
<table class="plans"><tr><th></th><th>개인</th><th>팀</th></tr><tr><td>월 거래 내역</td><td>500건</td><td>무제한</td></tr></table>
```

> 에이전트 지시문: 가짜 3단 요금제 + 'Most Popular' 배지 금지. 실제 가격 정책이 있을 때만 비교표로.

**해결** — 본문·긴 문단은 좌측 정렬, 중앙 정렬은 짧은 hero 문구 정도로 제한한다.

1. text-center 사용처를 찾아 두 줄 이상 문단은 좌측 정렬로 바꾼다.

> 에이전트 지시문: 모든 텍스트 중앙 정렬 금지. 본문과 섹션 제목은 그리드 기준선에 맞춰 좌측 정렬.

**해결** — 섹션 밀도를 내용에 맞춰 조절한다: 핵심 섹션은 넉넉히, 보조 섹션은 촘촘히, 일부는 전폭으로.

1. 섹션마다 역할(강조/정보/전환)을 정하고 여백 토큰을 3단계로 나눠 적용한다.

```
.section--hero{padding-block:clamp(4rem,10vw,9rem)} .section--dense{padding-block:2.5rem}
```

> 에이전트 지시문: 모든 섹션에 같은 py 값을 쓰지 말 것. 내용 역할에 따라 섹션 밀도를 다르게.

#### LAY-06 보일러플레이트 푸터 (가짜 법적 링크·소셜)

2. 푸터에 만든 사람/팀의 실제 정보나 짧은 한 줄 소개를 넣는다.

```
<footer><p>서울에서 두 명이 만듭니다 · <a href="mailto:hi@realdomain.kr">hi@realdomain.kr</a></p></footer>
```

> 에이전트 지시문: 가짜 Privacy/Terms/소셜 링크(href='#') 금지. 실제 존재하는 정보만 푸터에.

#### CPY-01 AI 상투어 밀도 (elevate·seamless·혁신적인·원활한…)

**왜 슬롭으로 느끼나** — LLM은 마케팅 문구에서 'seamless, elevate, unlock, 혁신적인, 원활한, 차세대' 같은 단어를 사람보다 수 배 높은 빈도로 쓴다. 단어 하나하나는 문제가 아니지만, 짧은 카피에 몰려 있으면 독자는 즉시 '아무 말도 안 하는 글'로 느낀다.

**해결** — 모든 추상 형용사를 '구체적 사실(숫자, 대상, 상황)'로 바꾼다. 상투어 하나당 증거 하나.

1. 리포트에 나온 상투어를 전부 찾아 표시한다.
2. 각 문장에 '누가, 무엇을, 얼마나'가 들어가도록 다시 쓴다 (예: '원활한 협업' → '댓글 달면 담당자에게 슬랙 알림').
3. 형용사를 지웠을 때 문장이 무너지면, 그 문장은 원래 내용이 없었던 것 → 삭제한다.
4. 브랜드 보이스 3원칙(예: 짧게, 반말, 숫자 먼저)을 정하고 전체 카피를 통일한다.

```
Before: "Elevate your workflow with seamless, AI-powered collaboration."
After : "회의록을 붙여넣으면 할 일 7개가 담당자별로 나뉘어 나옵니다. 평균 40초."
```

> 에이전트 지시문: elevate/seamless/unlock/empower/cutting-edge/혁신적인/원활한/차세대/극대화 같은 추상 마케팅 어휘 금지. 모든 주장은 구체적 숫자·대상·상황으로 쓸 것.

#### CPY-02 플레이스홀더·더미 텍스트 잔존

**왜 슬롭으로 느끼나** — Lorem ipsum, 'Your Company', Acme, John Doe, 555 전화번호가 남아 있으면 '아무도 끝까지 확인하지 않았다'는 결정적 증거가 된다. 신뢰가 한 번에 무너진다.

**해결** — 모든 더미 텍스트·이름·연락처를 실제 내용으로 교체하거나, 내용이 없으면 해당 요소를 삭제한다.

1. 리포트의 위치를 따라 더미 텍스트를 전부 교체한다.
2. 실제 정보가 아직 없다면 블록 자체를 빼는 것이 가짜를 두는 것보다 낫다.
3. CI에 `slop-lens scan --fail-over` 또는 grep 검사를 걸어 재발을 막는다.

```
grep -rniE 'lorem ipsum|your company|acme|john doe|555-' src/
```

> 에이전트 지시문: Lorem ipsum, Your Company, Acme, John Doe, example.com, 555 번호 등 더미 텍스트 절대 금지. 모르면 해당 블록을 만들지 말 것.

#### CPY-03 꾸며낸 사회적 증거 (가짜 후기·통계·별점)

**왜 슬롭으로 느끼나** — 'Sarah Johnson, CEO at TechCorp ★★★★★', '10,000+ happy customers', '99.9% uptime'처럼 출처 없는 숫자와 전형적 이름은 AI가 빈칸을 채운 흔적이다. 사람들은 이런 후기를 '가짜'로 인지하고 사이트 전체를 불신한다.

**해결** — 검증 가능한 실제 증거만 남긴다. 없으면 '왜 믿을 수 있는지'를 다른 방식(제작 과정, 데모, 오픈 데이터)으로 보여준다.

1. 실제 사용자 후기가 없다면 후기 섹션을 삭제한다.
2. 후기를 쓴다면 실명·사진·링크(원문 트윗/리뷰) 등 출처를 함께 단다.
3. 통계는 측정 기간·기준을 명시한다 (예: '2025년 3월 베타 사용자 212명 기준').
4. 대안: 라이브 데모, 변경 로그, 창업자 소개로 신뢰를 만든다.

```
<blockquote cite="https://x.com/realuser/status/…">“…”<footer>— @realuser, 프리랜서 디자이너 (원문 링크)</footer></blockquote>
```

> 에이전트 지시문: 가짜 후기·가짜 이름(Sarah Johnson 등)·출처 없는 통계(10,000+ users, 99.9%)·별점 금지. 검증 가능한 증거만 사용.

#### CPY-04 공식형 헤드라인 ('The Future of X', 'X, Reimagined')

**왜 슬롭으로 느끼나** — 'The future of X', 'X reimagined', 'Everything you need to…', '모든 것을 한 곳에서' 같은 문형은 무엇에든 붙일 수 있는 문장이다. 제품명만 바꿔도 성립한다면 헤드라인이 아니다.

**해결** — 헤드라인을 '이 제품만 할 수 있는 구체적 약속'으로 바꾼다. 경쟁사 이름을 넣어도 성립하면 다시 쓴다.

1. 모든 h1~h3를 나열하고 '다른 제품 이름을 넣어도 말이 되는가?' 테스트를 한다.
2. 통과하지 못하면 대상(누구) + 결과(무엇이 달라지나) + 구체(숫자/장면)로 다시 쓴다.

```
Before: "The Future of Personal Finance"
After : "월급날 3분, 이번 달 고정지출이 정리됩니다"
```

> 에이전트 지시문: 'The future of', 'Reimagined', 'Everything you need', '모든 것을 한 곳에서' 같은 범용 헤드라인 금지. 제품 고유의 구체적 약속으로.

#### CPY-05 리듬형 3단 문구·대시 남용 ('Fast. Simple. Secure.')

**왜 슬롭으로 느끼나** — 세 단어 끊어치기('Fast. Simple. Secure.'), 'Not just X — it's Y' 구문, 과도한 em dash(—)는 LLM 문체의 대표 리듬이다.

**해결** — 끊어치기·대시 구문을 일반 문장으로 풀고, 세 가지 나열은 가장 중요한 하나만 남긴다.

1. 'A. B. C.' 형태의 문구를 하나의 구체적 문장으로 바꾼다.
2. em dash는 쉼표나 마침표로 바꾼다.
3. '~가 아니라 ~입니다' 대조 구문을 줄인다.

```
Before: "Fast. Secure. Reliable."
After : "1초 안에 결제 완료, 카드 정보는 저장하지 않습니다."
```

> 에이전트 지시문: 'A. B. C.' 3단 끊어치기, 'Not just X — it's Y' 구문, em dash(—) 남용 금지.

#### CPY-06 CTA 문구 단조로움 (Get Started / 더 알아보기 반복)

**왜 슬롭으로 느끼나** — 모든 버튼이 'Get Started', 'Learn More', '시작하기'면 버튼을 눌렀을 때 무슨 일이 일어나는지 알 수 없다. 행동 설계가 빠진 기본값이다.

**해결** — 각 CTA를 '누르면 일어나는 일'로 구체화한다.

1. 버튼별로 클릭 후 결과를 적어본다.
2. 그 결과를 버튼 문구로 쓴다 (예: '시작하기' → '내 카드 내역 불러오기').

```
<button>예시 데이터로 30초 체험</button>
```

> 에이전트 지시문: Get Started/Learn More/시작하기/더 알아보기 같은 범용 CTA 금지. 버튼 문구는 클릭 결과를 구체적으로 설명.

#### TXT-01 장식용 대문자 라벨 남발 (eyebrow·마이크로 라벨)

**왜 슬롭으로 느끼나** — 제목 위·패널 위마다 'NEXT-GEN PUZZLE', 'MISSION', 'STAGE SELECT'처럼 자간을 벌린 작은 대문자 라벨이 붙어 있다. 정보는 거의 없고 '세련돼 보이게' 하려는 장식인데, AI가 만든 랜딩 페이지·게임 UI에서 가장 흔한 문법이라 화면 곳곳에 반복되면 사람들은 바로 템플릿으로 느낀다. 한국어 화면에 영어 대문자 라벨이 섞이면 더 두드러진다.

**해결** — 정보가 없는 라벨은 지우고, 꼭 필요한 구분은 크기·굵기·여백으로 한다. 남길 라벨은 1화면 1개, 사용자 언어로.

1. 화면별 대문자 라벨을 나열하고 '지우면 정보가 사라지는가?'를 확인한다.
2. 사라지지 않는 라벨은 삭제한다.
3. 남길 라벨은 한국어로 바꾸고, 제목과 위계를 크기·굵기로 만든다.

```
<!-- 제거 --> <small class="eyebrow">NEXT-GEN PUZZLE</small>
<h1>게임 제목</h1>
```

> 에이전트 지시문: 제목 위 장식용 대문자 라벨(eyebrow)·자간 넓힌 마이크로 라벨 금지. 위계는 크기·굵기·여백으로.

#### TXT-02 아이콘·기호에 같은 뜻의 글자 중복 (↑ 위, ← 왼쪽)

**왜 슬롭으로 느끼나** — 화살표·기호 옆에 같은 뜻의 글자를 또 붙였다(↑ 위, ← 왼쪽, ▶ 다음). 기호만으로 충분한 곳에 설명을 덧붙이는 것은 AI가 '친절하게' 만들 때의 습관이고, 화면을 지저분하게 만든다.

**해결** — 기호만 남기거나, 글자만 남긴다. 조작 안내는 첫 1회만 보여준다.

1. 중복 라벨을 찾아 하나를 지운다.
2. 접근성용 설명은 aria-label로 옮긴다.

```
<button aria-label="위로 이동">↑</button>
```

> 에이전트 지시문: 기호·아이콘에 같은 뜻의 글자를 중복으로 붙이지 말 것.

#### TXT-03 설명·안내문 과잉

**왜 슬롭으로 느끼나** — 한 화면에 '~하세요', 'press ~', 'select ~ then ~' 같은 안내문이 여러 개 붙어 있다. 화면이 스스로 설명되지 않아서 글로 메운 것이고, 읽을 것이 많아 피로하다. 게임에서는 '해보며 배우는' 경험을 막는다.

**해결** — 안내문을 1~2개로 줄이고, 나머지는 화면 구성(강조, 하이라이트, 첫 판 튜토리얼)으로 대신한다.

1. 안내문을 모두 나열한다.
2. 첫 행동을 유도하는 1개만 남긴다.
3. 필요한 조작은 처음 시도할 때만 짧게 띄우고 사라지게 한다.

> 에이전트 지시문: 화면마다 안내문을 붙이지 말 것. 화면 구성으로 설명하고 안내는 첫 1회만.

#### TXT-04 단축키·조작 힌트 나열

**왜 슬롭으로 느끼나** — 'ARROWS NAVIGATE · ENTER CONFIRM', '되돌리기 (Z)', '다시 시작 (R)'처럼 조작 키가 화면 곳곳에 상시 표시된다. 개발 중 디버그 안내를 그대로 둔 것 같은 인상을 준다.

**해결** — 조작 힌트는 처음 한 번 또는 설정/도움말로 옮기고, 버튼에는 동작 이름만 남긴다.


> 에이전트 지시문: 단축키 힌트를 화면에 상시 나열하지 말 것.

#### TXT-05 개발용·임시 문구가 화면에 노출

**왜 슬롭으로 느끼나** — 'Unknown (Test)', 'BPM —', 'COVER —', 'undefined' 같은 개발용 값·빈칸 표시가 그대로 화면에 보인다. 사람은 이것을 '아직 아무도 완성하지 않은 화면'으로 읽고, 나머지가 아무리 정돈돼 보여도 껍데기로 느낀다.

**해결** — 모든 화면 값을 실제 데이터로 연결하고, 값이 없으면 해당 줄을 숨기거나 의미 있는 기본값을 보여준다.

1. 화면에 보이는 '—', Unknown, Test 값을 모두 찾는다.
2. 데이터를 연결하거나 행을 숨긴다.
3. 빌드 전 개발용 메타데이터를 제거한다.

```
bpmLabel.gameObject.SetActive(song.Bpm > 0);
```

> 에이전트 지시문: 개발용·임시 값(Unknown, Test, —, undefined)을 화면에 노출하지 말 것.

#### TXT-06 범용 태그라인·UI 상투 문구 (화면 기준)

**왜 슬롭으로 느끼나** — 'An adventure in motion', 'Your adventure begins', '지금 바로 도전해 보세요'처럼 어떤 게임·서비스에도 붙는 문장이 화면에 있다. 제목을 바꿔도 그대로 성립하는 문장은 아무 정보도 주지 않고, AI가 빈칸을 채운 흔적으로 읽힌다.

**해결** — 이 작품에만 해당하는 구체적인 한 문장으로 바꾼다 (무엇을 하는지 + 무엇이 다른지).

1. 태그라인에 다른 게임 이름을 넣어도 말이 되는지 확인한다.
2. 말이 되면 고유 메카닉·장면을 넣어 다시 쓴다.

```
'An adventure in motion' → '무너지는 탑을 밧줄 하나로 오르는 클라이밍 퍼즐'
```

#### IMG-01 AI 이미지 생성기 메타데이터가 남은 원본 에셋

**왜 슬롭으로 느끼나** — 이미지 안에 DALL·E/Midjourney/Stable Diffusion 프롬프트, C2PA 'AI 생성' 표기가 그대로 남아 있다는 것은 생성 결과를 편집 없이 바로 넣었다는 뜻이다. AI 이미지 사용 자체가 슬롭은 아니지만, 무보정 원본은 언캐니 아티팩트(손, 글자, 질감)를 함께 가져온다.

**해결** — AI 이미지는 '재료'로만 쓰고 반드시 사람의 편집(크롭·리터치·색 보정·합성·스타일 통일)을 거친다. 출처 표기 정책도 정한다.

1. 리포트의 이미지를 열어 손/글자/로고/대칭 오류를 확대 검수한다.
2. 브랜드 팔레트로 색 보정하고, 같은 프롬프트 스타일 가이드로 전체 에셋을 통일한다.
3. 가능한 핵심 이미지(hero, 제품, 캐릭터)는 실제 사진·직접 그린 일러스트로 교체한다.
4. 생성 이미지를 쓴다면 C2PA/IPTC 표기를 유지하되 alt와 캡션에 의도를 적는다 (투명성).

```
exiftool -a -G1 assets/hero.png   # 메타데이터 확인
(리터치 후) exiftool -overwrite_original -Parameters= assets/hero.png
```

> 에이전트 지시문: 생성 이미지를 무보정으로 쓰지 말 것. 모든 이미지는 하나의 스타일 가이드(팔레트·조명·선 굵기)로 통일하고 아티팩트를 검수할 것.

#### IMG-02 AI 생성기 기본 해상도 이미지 다수 (1024², 1792×1024…)

**왜 슬롭으로 느끼나** — 1024×1024, 1792×1024, 1536×1024 등은 이미지 생성기의 기본 출력 크기다. 크롭·리사이즈 없이 그대로 쓰였다는 약한 신호다 (단독으로는 판단하지 않음).

**해결** — 레이아웃 슬롯에 맞게 크롭하고 반응형 크기(srcset)로 다시 내보낸다.

1. 이미지가 들어갈 실제 비율(예: 4:5, 21:9)을 정하고 의도적으로 크롭한다.
2. AVIF/WebP + srcset으로 여러 크기를 만든다.

```
<img src="hero-1600.avif" srcset="hero-800.avif 800w, hero-1600.avif 1600w" sizes="100vw" alt="…">
```

> 에이전트 지시문: 이미지는 레이아웃 비율에 맞춰 의도적으로 크롭하고 srcset으로 제공.

#### IMG-03 AI 생성기 파일명 그대로 사용

**왜 슬롭으로 느끼나** — 'DALL·E 2025-…png', 'ChatGPT Image …', 'Gemini_Generated_Image_…', 'user_prompt_text_uuid.png' 같은 파일명은 생성 결과를 다운로드해 그대로 넣었다는 증거다.

**해결** — 에셋 파일명을 역할 기반으로 바꾸고 (hero-desk-morning.avif) 에셋 파이프라인(리사이즈·압축)을 거친다.

1. 파일명을 '용도-내용-변형' 규칙으로 바꾼다.
2. 참조 경로를 일괄 수정한다.

```
assets/DALL·E 2025-03-02 10.11.png → assets/hero-cafe-counter@2x.avif
```

> 에이전트 지시문: 에셋 파일명은 역할 기반 규칙으로. 생성기 기본 파일명 금지.

#### IMG-04 플레이스홀더 이미지 서비스 (picsum, pravatar, unsplash 랜덤…)

**왜 슬롭으로 느끼나** — picsum.photos, i.pravatar.cc, placehold.co, source.unsplash.com 같은 임시 이미지는 '내용 없이 자리만 채웠다'는 뜻이다. 특히 pravatar 얼굴 + 가짜 후기 조합은 가장 강한 슬롭 신호다.

**해결** — 모든 임시 이미지를 실제 에셋으로 교체하고, 없으면 이미지 슬롯 자체를 없앤다.

1. 리포트 위치의 URL을 실제 에셋 경로로 바꾼다.
2. 인물 아바타는 실제 사용자 동의를 받은 사진만 쓰거나 이니셜 배지로 대체한다.
3. 스톡 사진을 쓴다면 의도에 맞게 골라 크롭·색보정하고 로컬에 저장한다.

```
<img src="https://i.pravatar.cc/150?img=3"> → <span class="avatar" aria-hidden="true">JK</span>
```

> 에이전트 지시문: picsum/pravatar/placehold/unsplash 랜덤 등 플레이스홀더 이미지 금지.

#### IMG-05 실제 이미지가 하나도 없음 (아이콘·그라디언트뿐)

**왜 슬롭으로 느끼나** — 여러 섹션이 있는데 제품 화면·사진·일러스트가 전혀 없고 아이콘과 그라디언트만 있다면, 보여줄 '실체'가 없는 페이지로 읽힌다.

**해결** — 제품이 실제로 동작하는 장면 1~3개를 hero와 핵심 섹션에 넣는다.

1. 실제 화면을 캡처해 브라우저 프레임 없이 크롭한다.
2. 사용 맥락 사진 또는 직접 만든 일러스트를 추가한다.

```
<img src="/shots/budget-week.avif" alt="주간 예산이 초과된 카테고리가 빨갛게 표시된 실제 화면">
```

> 에이전트 지시문: 제품/게임의 실제 화면 또는 의도된 일러스트를 반드시 포함.

#### ART-01 가짜 픽셀아트 (생성 이미지의 픽셀 흉내)

**왜 슬롭으로 느끼나** — 멀리서 보면 픽셀아트지만 실제 픽셀 격자가 불규칙하고, 한 칸 안에 노이즈와 수만 가지 색이 섞여 있다. 이미지 생성기가 '픽셀아트 스타일'을 흉내 낸 전형적 결과라서, 진짜 픽셀아트 옆에 두면 흐릿하고 지저분해 보이고 사람들은 'AI로 뽑은 아이콘'이라고 바로 알아챈다.

**해결** — 픽셀아트라면 목표 해상도(예: 32×32)로 다시 그리거나, 생성 이미지를 축소·팔레트 양자화한 뒤 손으로 정리한다.

1. 아이콘 목표 해상도와 팔레트(16~32색)를 정한다.
2. 생성 이미지를 최근접 이웃으로 목표 해상도까지 줄이고 팔레트로 양자화한다.
3. 윤곽선·하이라이트를 픽셀 단위로 손으로 정리한다(Aseprite).
4. 게임에서는 정수 배율 + Point 필터로 확대한다.

```
# Aseprite: Sprite > Sprite Size 32x32 (Nearest) → Sprite > Color Mode > Indexed (palette 24색)
```

> 에이전트 지시문: 생성 이미지를 '픽셀아트 풍'으로 쓰지 말 것. 실제 픽셀 격자·제한 팔레트로 다시 그릴 것.

#### ART-02 한 세트 안에서 아트 스타일 혼재

**왜 슬롭으로 느끼나** — 같은 폴더(같은 용도)의 아이콘·스프라이트가 어떤 것은 픽셀아트, 어떤 것은 페인팅/글로우 스타일이다. 한 사람이 정한 아트 방향이 없다는 신호이고, 여러 번 생성해서 잘 나온 것만 모아 붙인 결과로 보인다.

**해결** — 세트마다 아트 바이블(해상도, 팔레트, 외곽선, 조명 방향)을 정하고 기준에서 벗어난 에셋을 다시 만든다.

1. 세트에서 가장 마음에 드는 1개를 기준으로 고른다.
2. 해상도·팔레트·테두리 규칙을 문서화한다.
3. 기준과 다른 에셋을 같은 규칙으로 다시 그린다.

> 에이전트 지시문: 같은 용도의 에셋은 하나의 아트 바이블(해상도·팔레트·외곽선)로 통일.

#### ART-03 AI 생성 이미지를 다듬지 않고 그대로 사용

**왜 슬롭으로 느끼나** — 생성기에서 나온 그림을 크기·색감·화풍을 손대지 않고 그대로 넣었다. 생성 이미지 특유의 매끈한 광택, 화면 구석까지 고르게 깔린 과한 디테일, 의미 없는 장식이 그대로 남아서 사람들은 '프롬프트 한 번 돌려서 붙였다'는 이질감을 바로 느낀다. 같은 AI 이미지라도 화풍을 맞추고 다듬으면 이 느낌이 크게 줄어든다 — 쓰느냐보다 '그대로 쓰느냐'가 문제다.

**해결** — 생성 이미지는 초안으로만 쓰고, 게임의 아트 방향(해상도·팔레트·외곽선·조명)에 맞춰 다시 그리거나 후보정한다.

1. 아트 바이블을 먼저 정한다(팔레트 16~32색, 외곽선 두께, 광원 방향, 디테일 밀도).
2. 생성 이미지를 그 기준으로 크롭·리사이즈하고 팔레트·색보정(LUT)을 한 번에 적용한다.
3. 초점이 되는 부분만 디테일을 남기고 나머지는 단순화한다(실루엣이 읽히게).
4. 의미 없는 장식·뭉개진 글자·손가락 같은 아티팩트를 손으로 지운다.
5. 카드·배경처럼 반복되는 이미지는 같은 프레임·같은 조명으로 통일한다.

```
# 일괄 톤 맞춤: magick in.png -resize 640x -modulate 100,85 -posterize 24 -remap palette.png out.png
```

> 에이전트 지시문: 생성 이미지를 생성기 출력 그대로 쓰지 말 것. 아트 바이블에 맞춰 리사이즈·팔레트·보정·아티팩트 제거 후 사용.

#### ART-04 이미지마다 조명·색감이 제각각 (톤 통일 안 됨)

**왜 슬롭으로 느끼나** — 같은 게임 안의 그림들이 하나는 어둡고 채도 낮은 사진풍, 하나는 밝고 쨍한 일러스트처럼 장마다 조명과 색감이 다르다. 프롬프트를 장마다 따로 돌리면 생기는 전형적 결과로, 한 세계의 그림이 아니라 '여러 번 뽑아 모은 그림'으로 보인다.

**해결** — 모든 그림에 같은 색보정(LUT)·같은 광원 방향·같은 채도 범위를 적용해 한 세계의 톤으로 묶는다.

1. 기준 이미지 1장을 정하고 그 명도·채도·색온도를 수치로 기록한다.
2. 나머지 이미지를 같은 LUT로 보정한다.
3. 보정해도 안 맞는 이미지는 다시 만든다.

> 에이전트 지시문: 모든 일러스트를 하나의 LUT·광원·채도 범위로 통일.

#### UX-01 죽은 링크·빈 버튼 (href="#", onClick={() => {}})

**왜 슬롭으로 느끼나** — 겉으로는 완성된 내비게이션·버튼인데 눌러도 아무 일이 없다. '보기엔 그럴듯하지만 동작하지 않는' 것은 AI 슬롭을 가장 확실하게 체감시키는 경험이다.

**해결** — 모든 링크/버튼에 실제 목적지 또는 동작을 연결하고, 준비되지 않은 기능은 노출하지 않는다.

1. href='#' 목록을 뽑아 각 항목을 (1) 실제 URL/앵커 연결 (2) 삭제 (3) '준비 중' 비활성 표시 중 하나로 처리한다.
2. 빈 onClick 핸들러를 실제 동작으로 구현하거나 버튼을 제거한다.
3. Playwright 등으로 모든 링크 클릭 테스트를 자동화한다.

```
<a href="#pricing">가격</a>  <!-- 실제 존재하는 id로 -->
<button disabled aria-describedby="soon">팀 플랜</button><span id="soon">5월 출시</span>
```

> 에이전트 지시문: href='#' 또는 빈 핸들러 금지. 동작하지 않는 UI는 만들지 말 것.

#### UX-02 가짜 폼 제출 (alert/console.log로 '감사합니다')

**왜 슬롭으로 느끼나** — 뉴스레터·문의 폼이 실제로 어디에도 전송하지 않고 alert('Thanks for subscribing!')만 띄운다. 사용자를 속이는 UI는 신뢰를 직접 깎는다.

**해결** — 폼을 실제 백엔드(또는 Formspree/Netlify Forms 등)에 연결하고, 로딩·성공·실패 상태를 화면 안에서 보여준다.

1. action/fetch 대상 엔드포인트를 연결한다.
2. 제출 중 버튼 비활성 + 스피너, 성공/실패 메시지를 인라인으로 표시한다.
3. 연결할 수 없다면 폼을 빼고 메일 링크로 대체한다.

```
const r = await fetch('/api/subscribe',{method:'POST',body:new FormData(form)});
status.textContent = r.ok ? '구독 완료! 첫 메일은 금요일에 갑니다.' : '실패했어요. 잠시 후 다시 시도해주세요.';
```

> 에이전트 지시문: 제출이 실제로 일어나지 않는 가짜 폼 금지. 폼은 실제 전송 + 로딩/성공/실패 상태를 가져야 함.

#### UX-03 포커스·상태 디자인 부재

**왜 슬롭으로 느끼나** — hover 효과는 화려한데 키보드 포커스, 로딩, 비어 있음, 오류 상태가 전혀 없다. 데모 캡처용으로만 설계된 UI의 전형이다.

**해결** — :focus-visible 스타일과 loading/empty/error 상태를 정의한다.

1. 버튼·링크·입력에 :focus-visible 아웃라인을 추가한다.
2. 데이터를 보여주는 컴포넌트마다 빈 상태·오류 상태 문구를 작성한다.

```
:where(a,button,input):focus-visible{outline:2px solid var(--brand);outline-offset:2px}
```

> 에이전트 지시문: 모든 인터랙티브 요소에 focus-visible 스타일, 데이터 영역에 로딩/빈/오류 상태를 포함.

#### UX-04 hover 리프트·transition-all 남발

**왜 슬롭으로 느끼나** — 모든 카드가 hover 시 살짝 떠오르고(scale-105, -translate-y-1) transition-all duration-300이 붙는 것은 AI 컴포넌트의 습관이다. 의미 없는 움직임은 피로감을 준다.

**해결** — 모션은 '상태 변화를 설명할 때'만 쓴다. 클릭 가능한 요소에만 절제된 피드백을 준다.

1. transition-all → 필요한 속성만(transition: background-color 120ms).
2. 클릭 불가능한 카드의 hover 효과를 제거한다.
3. prefers-reduced-motion을 존중한다.

```
.btn{transition:background-color .12s ease}
@media (prefers-reduced-motion:reduce){*{transition:none!important}}
```

> 에이전트 지시문: hover:scale/translate 리프트와 transition-all 남발 금지. 모션은 상태 변화 설명에만.

#### UX-05 반응형 대응 없음

**왜 슬롭으로 느끼나** — 데스크톱 스크린샷 한 장을 위해 만들어진 페이지는 모바일에서 깨진다. 사람들은 AI 결과물을 '폰에서 열었을 때' 가장 먼저 슬롭으로 판정한다.

**해결** — viewport 메타 + 모바일 우선 레이아웃 + 유동 타이포(clamp)를 적용하고 360px 폭에서 검수한다.

1. <meta name=viewport content="width=device-width, initial-scale=1">를 추가한다.
2. 고정 px 폭을 max-width + %/fr로 바꾼다.
3. 360/768/1280px에서 스크린샷 비교 검수한다.

```
h1{font-size:clamp(2rem,6vw,4.5rem)} .grid{grid-template-columns:repeat(auto-fit,minmax(min(100%,18rem),1fr))}
```

> 에이전트 지시문: 모바일 360px 폭에서 깨지지 않게 반응형으로 설계 (viewport 메타, 유동 레이아웃, clamp 타이포).

#### UX-06 스크롤 페이드인 일괄 적용

**왜 슬롭으로 느끼나** — 모든 섹션이 스크롤 시 아래에서 위로 fade-in(AOS, whileInView, opacity:0→1)하는 연출은 AI 페이지의 기본 '고급스러움' 처리다. 내용 읽기를 지연시킨다.

**해결** — 스크롤 애니메이션을 제거하거나, 이야기가 있는 1곳(데모 시퀀스 등)에만 남긴다.

1. data-aos / whileInView / fade-in 클래스를 일괄 제거한다.
2. 정말 필요한 1곳은 내용 이해를 돕는 단계적 노출로 설계한다.

```
<!-- 제거: data-aos="fade-up" -->
```

> 에이전트 지시문: 모든 섹션 스크롤 fade-in 금지. 애니메이션은 내용 이해를 돕는 1곳 이하.

#### UX-07 네이티브 alert/confirm/prompt 사용

**왜 슬롭으로 느끼나** — 브라우저 기본 alert 창은 디자인된 경험을 단번에 깨뜨리고 '시제품/데모 코드'라는 인상을 준다.

**해결** — 인라인 메시지, 토스트, 모달(<dialog>) 등 디자인 시스템 안의 피드백으로 교체한다.

1. alert/confirm/prompt 호출을 찾아 용도별(정보/확인/입력)로 대체 UI를 만든다.

```
<dialog id="confirm"><p>정말 삭제할까요?</p><button value="ok">삭제</button></dialog>
```

> 에이전트 지시문: alert/confirm/prompt 사용 금지. 피드백은 디자인된 인라인 UI로.

#### RND-12 모바일 레이아웃 붕괴 (390px 실측)

**왜 슬롭으로 느끼나** — 휴대폰 폭(390px)으로 열었을 때 viewport 설정이 없어 데스크톱 화면이 축소되어 보이거나, 가로로 넘쳐 좌우 스크롤이 생긴다.

**해결** — viewport 메타 + 유동 레이아웃으로 바꾸고 390px에서 다시 확인한다.

1. <meta name=viewport content="width=device-width, initial-scale=1"> 추가.
2. 넘치는 요소(리포트 선택자)의 고정 폭 제거.

```
img,video,canvas{max-width:100%;height:auto}
```

> 에이전트 지시문: 390px 폭에서 축소·가로 넘침 없이.

#### RND-14 죽은 클릭 (실제 클릭 테스트)

**왜 슬롭으로 느끼나** — 화면의 버튼·링크를 실제로 눌러봤더니 화면·주소·네트워크 어디에도 변화가 없다. 정적 추정이 아니라 실측이다. '그럴듯해 보이는데 아무것도 안 되는' 경험은 AI 슬롭을 가장 확실하게 체감시킨다.

#### COD-01 AI 스캐폴딩 주석 ('In a real app…', 'Add more…', 'TODO: implement')

**왜 슬롭으로 느끼나** — 'In a real application you would…', 'Replace with your API key', 'Add more items as needed', '실제 서비스에서는…' 같은 주석은 LLM이 미완성 부분을 사람에게 떠넘긴 흔적이다. 이 주석이 남아 있으면 해당 기능이 실제로는 구현되지 않았을 가능성이 높다.

**해결** — 주석이 가리키는 미구현 부분을 실제로 구현하거나, 기능 자체를 제거한 뒤 주석을 삭제한다.

1. 리포트 위치의 주석을 하나씩 열어 '무엇을 미뤘는지' 확인한다.
2. mock/simulate 코드는 실제 API 호출로 교체하거나 데모임을 UI에 명시한다.
3. 남길 주석은 '왜(why)'를 설명하는 것만 남긴다.

```
// In a real app, fetch from API  ← 삭제
const res = await fetch('/api/items'); // 캐시 5분: 대시보드 새로고침 폭주 방지
```

> 에이전트 지시문: 'In a real app', 'Add more', 'Replace with your', 'TODO: implement', '실제 서비스에서는' 류의 미루기 주석과 mock/simulate 코드 금지. 끝까지 구현할 것.

#### COD-02 코드를 그대로 읽어주는 주석 ('// Function to handle click')

**왜 슬롭으로 느끼나** — '// Get the button element', '// Add event listener', '// Update the score' 처럼 코드를 한 줄씩 번역한 주석은 LLM 코드의 강한 특징이다.

**해결** — 무엇(what)을 설명하는 주석은 지우고, 이유(why)·제약·트레이드오프만 남긴다.

1. 리포트의 주석을 삭제한다.
2. 이름이 의도를 드러내도록 함수·변수명을 개선한다.

```
// Update the score  ← 삭제
// 콤보 3 이상부터 배율 적용: 초반 난이도 완화를 위해  ← 유지
```

> 에이전트 지시문: 코드를 그대로 설명하는 주석 금지. 주석은 이유와 제약만.

#### GAM-03 프로그래머 아트 (사각형·원만으로 렌더링)

**왜 슬롭으로 느끼나** — 플레이어·적·아이템이 모두 fillRect/arc 단색 도형이면 '프로토타입을 그대로 출시한' 느낌이 된다. 장르를 막론하고 시각적 정체성이 없다.

**해결** — 하나의 아트 방향(팔레트 4~8색, 해상도, 선 규칙)을 정하고 핵심 오브젝트부터 스프라이트로 교체한다.

1. 아트 방향을 1문장으로 정한다 (예: '16색 픽셀아트, 2px 외곽선, 따뜻한 석양 팔레트').
2. 플레이어 → 적 → 투사체 → 배경 순으로 교체한다 (가장 많이 보는 것부터).
3. 도형을 유지한다면 '의도된 미니멀리즘'으로: 제한 팔레트, 두께 있는 외곽선, 모양 언어(삼각형=위험) 정의.

```
const img=new Image();img.src='sprites/player.png';
ctx.imageSmoothingEnabled=false;ctx.drawImage(img,frame*16,0,16,16,x,y,32,32);
```

> 에이전트 지시문: 단색 사각형/원 프로그래머 아트 금지. 하나의 아트 방향(제한 팔레트·해상도·외곽선 규칙)으로 스프라이트를 통일.

#### GAM-04 게임필(Juice) 부재 — 타격감·피드백 없음

**왜 슬롭으로 느끼나** — 맞히거나 맞았을 때 화면 흔들림·파티클·히트스톱·플래시·이징이 전혀 없으면 조작이 '숫자가 바뀌는 것'으로만 느껴진다. 사람이 'AI가 만든 게임 같다'고 말하는 가장 큰 이유가 이 빈 손맛이다.

**해결** — 핵심 동사(점프·공격·수집) 1개에 피드백 레이어를 5겹 쌓는다: 예비동작 → 이펙트 → 사운드 → 카메라 → 여운.

1. 게임의 핵심 행동 1개를 고른다.
2. 명중 시: 2~4프레임 히트스톱 + 흰색 플래시 + 파티클 8~12개 + 짧은 카메라 흔들림.
3. 이동은 lerp/easing으로 가감속을 준다.
4. 같은 사운드라도 피치를 ±5% 랜덤화한다.
5. 효과마다 on/off 토글을 두고 비교 플레이해 강도를 조정한다.

```
function onHit(e){hitStop=0.05;shake=6;e.flash=0.08;spawnParticles(e.x,e.y,10);sfx.hit.play({rate:0.95+Math.random()*0.1})}
// render: ctx.translate((Math.random()-.5)*shake,(Math.random()-.5)*shake); shake*=0.9;
```

> 에이전트 지시문: 핵심 행동마다 히트스톱·플래시·파티클·카메라 흔들림·사운드 피드백을 넣을 것. 이동은 가감속(easing) 적용.

#### GAM-05 사운드 없음

**왜 슬롭으로 느끼나** — 게임 체감의 절반은 소리다. 효과음·배경음이 전혀 없으면 미완성 데모로 인식된다.

**해결** — 핵심 행동 3~5개에 효과음, 루프 BGM 1개, 음소거 토글을 추가한다.

1. jsfxr/ChipTone 등으로 효과음을 만든다 (점프, 명중, 획득, 피격, 게임오버).
2. 첫 입력 이후 AudioContext를 resume 한다 (자동재생 정책).
3. 볼륨/음소거 설정을 제공한다.

```
const sfx={jump:new Audio('sfx/jump.wav')};
function play(s){const a=s.cloneNode();a.volume=settings.sfx;a.play()}
```

> 에이전트 지시문: 핵심 행동 효과음 + BGM + 음소거 토글 필수.

#### GAM-07 난이도 곡선 없음 (고정 스폰·속도)

**왜 슬롭으로 느끼나** — 처음부터 끝까지 같은 속도·같은 스폰 간격이면 30초 안에 지루해진다. 사람이 설계한 게임은 긴장과 이완의 곡선이 있다.

**해결** — 시간/점수에 따른 난이도 곡선과 패턴(웨이브)을 데이터로 정의한다.

1. 0~30초 학습, 30~90초 상승, 이후 변주 구간을 정한다.
2. 스폰 간격·적 속도·패턴을 테이블로 만들고 곡선으로 보간한다.
3. 주기적으로 '쉬는 구간'을 넣는다.

```
const waves=[{t:0,interval:1.4,types:['walker']},{t:30,interval:1.0,types:['walker','dasher']},{t:75,interval:0.8,types:['dasher','splitter']}];
```

> 에이전트 지시문: 시간/점수 기반 난이도 곡선과 웨이브 테이블을 설계. 고정 스폰 금지.

#### GAM-08 게임 상태 흐름 없음 (타이틀·일시정지·메뉴)

**왜 슬롭으로 느끼나** — 페이지를 열자마자 게임이 시작되고 일시정지도 메뉴도 없다. 시작-플레이-종료-재도전의 흐름이 없으면 '테크 데모'로 느껴진다.

**해결** — 상태 머신(title → play → pause → over)을 도입한다.

1. mode 변수와 상태별 update/render를 분리한다.
2. Esc/P로 일시정지, 탭 비활성 시 자동 일시정지(visibilitychange).

```
const S={title:{update:t=>{if(keys.Enter)go('play')}},play:{…},pause:{…},over:{…}};
document.addEventListener('visibilitychange',()=>document.hidden&&go('pause'));
```

> 에이전트 지시문: title/play/pause/over 상태 머신과 일시정지(Esc/P, 탭 비활성 시 자동) 필수.

#### GAM-09 AI식 범용 게임 제목 (Neon Dash, Cosmic Defender…)

**해결** — 게임의 고유 메카닉이나 세계관의 구체 명사로 제목을 짓는다.

```
Neon Dash → '야간 택배: 마지막 한 집'
```

#### GAM-01 setInterval 게임 루프

**왜 슬롭으로 느끼나** — setInterval(update, 16) 루프는 화면 주사율과 맞지 않아 끊김(jank)을 만들고 탭 전환 시 폭주한다. 'AI가 최소 동작만 만든 게임'의 기술적 지문이다.

**해결** — requestAnimationFrame + 고정 timestep(또는 delta time) 루프로 교체한다.

1. setInterval 루프를 rAF 루프로 바꾼다.
2. update(dt)와 render()를 분리한다.

```
let last=performance.now(),acc=0;const STEP=1/60;
function frame(t){acc+=Math.min(.25,(t-last)/1000);last=t;
 while(acc>=STEP){update(STEP);acc-=STEP}render();requestAnimationFrame(frame)}
requestAnimationFrame(frame);
```

> 에이전트 지시문: 게임 루프는 requestAnimationFrame + 고정 timestep(delta time)으로.

#### GAM-02 프레임 독립 이동 없음 (delta time 미사용)

**해결** — 모든 이동·타이머에 dt(초)를 곱한다. Unity는 Time.deltaTime, Godot은 delta를 사용한다.

2. update(dt)에서 pos += vel * dt 로 바꾼다.


> 에이전트 지시문: 이동/타이머는 delta time 기반(px/초)으로.

#### GAM-10 고정 캔버스 크기 (리사이즈·DPR 미대응)

**왜 슬롭으로 느끼나** — 800×600 고정 캔버스는 고해상도 화면에서 흐릿하고 모바일에서 잘린다.

```
function fit(){const s=Math.floor(Math.min(innerWidth/W,innerHeight/H))||1;const d=devicePixelRatio||1;

```

#### AUD-01 합성 단음 효과음 (오실레이터 비프)

**왜 슬롭으로 느끼나** — 효과음이 녹음·디자인된 소리가 아니라 사인파/사각파 하나를 짧게 울린 '비프'다. 사람 귀에는 장난감·테스트 소리처럼 들려서 화면이 아무리 정돈돼 있어도 '코드로 대충 붙인 소리' = AI 슬롭으로 느껴진다. 행동마다 소리의 질감이 같아서 타격·획득·실패가 구별되지 않는다.

**해결** — 핵심 행동마다 질감이 다른 실제 효과음을 쓰고, 합성음을 쓴다면 레이어·엔벨로프·필터·변주를 설계한다.

1. 게임 핵심 행동 4~6개(이동, 성공, 실패, UI 확인, 보상)를 정하고 각자 다른 재료(마찰음, 금속, 눈 밟는 소리 등)로 만든다.
2. 효과음 라이브러리(Freesound CC0, Sonniss GDC 번들 등)나 직접 녹음한 소리를 편집해 쓴다.
3. 합성으로 만든다면 노이즈+톤 레이어, ADSR 엔벨로프, 로우패스 필터 스윕, 짧은 리버브를 넣는다.
4. 같은 소리라도 재생마다 피치 ±5%, 볼륨 ±2dB 무작위 변주를 준다.

```
// 눈 치우기 한 칸: 노이즈 버스트(눈) + 낮은 톤(삽) 레이어, 필터 스윕, 피치 변주
const n = noiseSource(ctx, 0.18); const f = ctx.createBiquadFilter(); f.type='lowpass';
f.frequency.setValueAtTime(3200, t); f.frequency.exponentialRampToValueAtTime(600, t+0.18);
n.playbackRate.value = 0.95 + Math.random()*0.1;
```

> 에이전트 지시문: 효과음을 오실레이터 단음(사인/사각파 비프)으로 만들지 말 것. 행동마다 질감이 다른 실제/디자인된 소리 + 재생마다 변주.

#### AUD-02 같은 소리의 기계적 반복 (변주 없음)

**왜 슬롭으로 느끼나** — 서로 다른 행동에 같은 소리가, 또는 같은 행동에 매번 완전히 똑같은 소리가 난다. 사람은 몇 번만 들어도 반복을 알아채고 '대충 붙인 소리'로 느낀다.

**해결** — 행동별로 소리를 나누고, 같은 행동은 2~4개 변형을 번갈아 쓰거나 피치·볼륨을 무작위로 바꾼다.

1. 행동→소리 대응표를 만든다.
2. 자주 나는 소리는 변형 3개 이상 + 피치 ±5% 랜덤.
3. 연속 재생 시 같은 변형이 두 번 연속 나오지 않게 한다.

```
src.pitch = Random.Range(0.95f, 1.05f); src.PlayOneShot(clips[Random.Range(0, clips.Length)]);
```

> 에이전트 지시문: 같은 효과음을 변주 없이 반복하지 말 것 (변형 여러 개 + 피치/볼륨 랜덤).

#### AUD-03 효과음이 없거나 극히 빈약함

**왜 슬롭으로 느끼나** — 게임인데 행동에 반응하는 소리가 없고 배경음악만 흐른다. 입력에 소리 피드백이 없으면 손맛이 사라지고, '프로토타입을 그대로 낸' 인상이 된다.

**해결** — 입력·판정·보상·실패·UI에 반응하는 효과음 세트를 만든다.

1. 리듬게임이라면 판정별 히트음(Perfect/Great/Miss)과 콤보·실패음을 따로 만든다.
2. UI 이동·확인·취소음을 넣는다.
3. 음악과 효과음의 음량 비율을 조정할 믹서 그룹을 둔다.

> 에이전트 지시문: 입력·판정·보상·실패·UI마다 효과음 필수.

#### AUD-04 AI 음악 생성기 흔적

**왜 슬롭으로 느끼나** — 음악 파일 메타데이터에 Suno·Udio 같은 생성기 표기가 남아 있다. 생성 음악 자체가 문제는 아니지만, 다듬지 않은 원본은 구조가 평이하고 게임 상황과 맞물리지 않아 '배경에 깔린 무언가'로 들린다.

**해결** — 생성 음악은 게임 구간·템포·루프 지점에 맞게 편집하고, 핵심 테마는 직접 작곡하거나 편곡한다.

1. 루프 지점·인트로·클라이맥스를 게임 흐름에 맞춰 자른다.
2. 상황별(평상·위기·보상) 변주를 만든다.

> 에이전트 지시문: 생성 음악은 게임 흐름에 맞게 편집·변주해서 쓸 것.

#### AUD-05 플레이 대부분이 무음

**왜 슬롭으로 느끼나** — 자동 플레이 동안 녹음된 소리의 대부분이 무음이다. 배경음·환경음이 없으면 공간감이 없고 화면이 '비어 있는' 느낌이 든다.

**해결** — 배경음악 또는 환경음(바람, 군중, 기계음)을 깔고, 행동 효과음과 음량 균형을 맞춘다.


> 에이전트 지시문: 플레이 중 배경음/환경음이 항상 흐르게 할 것.

#### A11Y-01 기본값 문서 제목 / lang 속성 누락

**왜 슬롭으로 느끼나** — 브라우저 탭에 'Vite + React', 'Document', 'My Website'가 떠 있거나 <html lang>이 없으면 아무도 마무리하지 않았다는 신호다. 공유 링크 미리보기에서도 그대로 노출된다.

**해결** — 페이지마다 고유한 <title>과 올바른 lang 속성을 지정한다.

1. '제품명 — 핵심 가치 한 줄' 형식으로 title을 쓴다.
2. <html lang="ko"> 등 실제 언어를 지정한다.

```
<html lang="ko"><title>잔고 — 월급날 3분 가계부</title>
```

> 에이전트 지시문: 고유한 <title>과 올바른 <html lang> 지정.

#### A11Y-02 공유 메타데이터·파비콘 누락

**왜 슬롭으로 느끼나** — meta description, og:image가 없고 파비콘이 vite.svg/기본값이면 링크를 공유했을 때 '빈 카드'가 나온다. 출시를 고려하지 않은 결과물로 보인다.

**해결** — description, og:title/og:image, 고유 파비콘을 추가한다.

1. 1200×630 공유 이미지를 만든다.
2. 브랜드 마크로 SVG 파비콘을 만든다.

```
<meta name="description" content="…">
<meta property="og:image" content="https://…/og.png">
<link rel="icon" href="/favicon.svg">
```

> 에이전트 지시문: meta description, og 태그, 고유 파비콘 포함.

#### A11Y-03 이미지 대체텍스트 누락·무의미 (alt="image")

**왜 슬롭으로 느끼나** — alt가 없거나 'image', 'hero image', 'placeholder'인 것은 이미지의 의미를 아무도 생각하지 않았다는 뜻이다.

**해결** — 이미지마다 '무엇을 보여주는지'를 문장으로 쓰고, 장식 이미지는 alt=""로 명시한다.

1. 정보 이미지: 내용과 맥락을 쓴다.
2. 장식 이미지: alt="" + aria-hidden.

```
<img src="week.avif" alt="식비가 주간 예산을 12% 초과했다고 표시된 화면">
```

> 에이전트 지시문: 모든 이미지에 의미 있는 alt (장식은 alt="").

#### A11Y-04 클릭 가능한 div/span (버튼 아님)

**왜 슬롭으로 느끼나** — onClick이 붙은 div는 키보드·스크린리더로 조작할 수 없다. 시각적으로만 동작하는 UI다.

**해결** — 클릭 요소는 <button> 또는 <a>로 바꾼다.

1. onClick 있는 div/span을 button으로 교체하고 스타일을 초기화한다.

```
<div onClick={open}> → <button type="button" onClick={open}>
```

> 에이전트 지시문: 클릭 요소는 반드시 button/a 사용.

#### A11Y-05 프레임워크 기본 보일러플레이트 잔존

**왜 슬롭으로 느끼나** — 'Edit src/App.jsx and save', 'count is 0', vite.svg/react.svg 로고, App.css 기본 스타일이 남아 있으면 생성 후 정리 단계가 없었다는 뜻이다.

**해결** — 템플릿 기본 파일·문구·로고·CSS를 제거한다.

1. App.css/index.css의 기본 템플릿 스타일(#root max-width 1280px 등)을 삭제한다.
2. 기본 로고 에셋과 카운터 예제를 제거한다.

```
rm src/assets/react.svg public/vite.svg
```

> 에이전트 지시문: 프레임워크 템플릿 기본 코드·로고·문구를 모두 제거.

#### RND-10 텍스트 대비 부족 (WCAG 실측)

**왜 슬롭으로 느끼나** — 실제 배경색 위에서 글자 대비가 WCAG 기준(본문 4.5:1, 큰 글자 3:1)에 못 미친다. 회색 글씨를 어두운 배경에 얹는 AI 다크 테마에서 특히 흔하며, 읽기 힘든 화면은 '덜 만든' 인상을 준다.

**해결** — 본문 대비 4.5:1 이상이 되도록 글자색 토큰을 조정한다.

1. 리포트의 대비값이 낮은 텍스트부터 색을 올린다.
2. muted 색 토큰 하나를 정의해 모든 보조 텍스트에 일괄 적용한다.

```
:root{--muted:#a39b8f} /* #15120f 배경에서 7.1:1 */
```

> 에이전트 지시문: 모든 텍스트는 WCAG AA 대비(4.5:1, 큰 글자 3:1) 이상.

#### RND-11 깨진 리소스·런타임 오류

**왜 슬롭으로 느끼나** — 페이지를 열면 404 리소스(이미지·스크립트·사운드)나 자바스크립트 오류가 발생한다. 생성된 코드가 존재하지 않는 파일을 참조하는 일은 AI 결과물에서 매우 흔하다.

**해결** — 참조된 모든 파일이 실제로 존재하는지 확인하고, 런타임 오류를 0으로 만든다.

1. 리포트의 실패 URL을 실제 에셋으로 채우거나 참조를 제거한다.
2. 브라우저 콘솔 오류를 하나씩 해결한다.

> 에이전트 지시문: 존재하지 않는 파일 참조와 콘솔 오류 0개.

#### RND-13 너무 작은 터치 영역·글자 (모바일 실측)

**왜 슬롭으로 느끼나** — 모바일에서 버튼·링크의 터치 영역이 24px보다 작거나 12px 미만 글자가 많아 손가락으로 쓰기 어렵다.

**해결** — 터치 대상은 최소 24px(권장 44px), 본문은 16px 이상.

1. 작은 대상에 padding을 추가한다.

```
nav a{display:inline-block;padding:.6rem .4rem}
```

> 에이전트 지시문: 모바일 터치 대상 최소 24px, 본문 16px.

#### RND-15 키보드 포커스 표시 없음 (Tab 실측)

**왜 슬롭으로 느끼나** — Tab 키로 이동했을 때 포커스된 요소의 모습이 전혀 바뀌지 않는다 (outline:none 등으로 제거됨).

> 에이전트 지시문: 모든 인터랙티브 요소에 보이는 focus-visible 스타일.

#### UNI-05 기본 문구('New Text', 'Button') 잔존

**왜 슬롭으로 느끼나** — 씬·프리팹에 'New Text', 'Button' 같은 생성 직후 기본 문구가 남아 있다. 화면에 노출되면 즉시 미완성으로 보인다.

**해결** — 기본 문구를 실제 문구로 바꾸거나 사용하지 않는 오브젝트를 지운다.


> 에이전트 지시문: 'New Text'/'Button' 등 기본 문구 금지.


## 5. 점수 계산

1. 규칙이 발동하면 **증거량 = 가중치(1~5) × 강도(0~1)**. 강도는 발생 횟수가 `발동 기준`에서 `최대 강도` 사이일 때 0.4→1.0으로 증가한다 (상투어 밀도처럼 비율 기반 규칙은 자체 계산).
2. **영역 점수** = 100·(1 − e^(−Σ증거량/6)). 포화형이라 약한 신호가 많이 쌓이면 올라가지만 100을 넘지 않는다.
3. **정적 Slop Index** = 0.3·가중평균(영역) + 0.4·상위3영역 평균 + 0.3·최고 영역 + 수렴 가산(45점 이상 영역이 2개를 넘을 때마다 +4, 최대 +12).
   사람은 가장 눈에 띄는 문제와, 여러 영역에서 동시에 나타나는 신호로 판단하기 때문에 최악의 영역과 동시 발생에 무게를 둔다.
4. **시각 검토** (멀티모달 에이전트가 스크린샷/플레이로 판정): yes=1, partial=0.5, no=0, na=제외 → 가중 평균 → 최종 = (1−a)·정적 + a·시각, a = 0.45 × 응답 비율.
5. **신뢰도**: 마크업·텍스트량·스타일·이미지·렌더 실측·시각 검토 응답 비율로 높음/보통/낮음. 렌더 실측이 없으면 색·대비·클릭·모바일·게임 런타임이 추정치이고, 시각 검토가 없으면 이미지 품질과 레이아웃 감각이 반영되지 않는다.

## 6. 지각 리뷰 (판정의 핵심)

슬롭인지는 사람이 판단한다. 리뷰어(이미지를 볼 수 있는 에이전트 또는 사람)가 SlopLens가 만든 화면 시트·에셋 시트·플레이 프레임·사운드 분석을 보고 감각별로 레벨·근거·이유·해결을 답한다. 리뷰가 있으면 **최종 = 0.65 × 지각 지수 + 0.35 × 측정 근거 지수**로 확정하고, 없으면 측정 근거만으로 **잠정** 판정한다.

레벨: 0 공들인 결과물 · 1 사소함 · 2 눈에 띔 · 3 슬롭으로 느껴짐 · 4 명백한 슬롭

|---|---|---|---|
| S1 | 첫인상 (3초) | 처음 3초에 '어디서 본 AI 생성물' 느낌이 드는가? 무엇 때문인가? | 1.5 / 1.5 |

### 공들인 흔적 실측 (웹)

커스텀 폰트, 직접 정의한 모션 곡선, 다양한 레이아웃 그리드, OpenType/가변폰트 설정, SVG 일러스트, 큰 이미지·영상을 실측해 0~100점을 낸다. AI가 흉내 내는 원본(예: Stripe)은 표면 패턴을 공유하지만 이런 디테일이 많다 → AI 지문 신호를 최대 60%까지 낮춰 반영한다.

## 8. 오탐 방지 원칙

- **단일 신호로 단정하지 않는다.** 대부분의 규칙은 여러 번 반복될 때만 발동하고(`발동 기준`), 점수는 여러 영역에서 수렴할 때 크게 오른다.
- **상투어는 밀도로 본다.** 300단어 이상이면 1000단어당 6회 미만은 무시한다.
- **약한 신호는 가중치가 낮다.** 예: AI 기본 해상도(IMG-02)는 가중치 1, 이미지 2장 이상일 때만.
- **C2PA는 약한 증거로만 센다.** 카메라·편집기도 C2PA를 남기므로 생성기 이름이 없으면 0.5로 계산.
- **검사기를 속이는 수정은 해결이 아니다.** 목표는 점수가 아니라 사람이 받는 인상이다. 가짜 후기를 더 그럴듯한 가짜로 바꾸는 것은 금지.
- **측정이 추정을 이긴다.** 렌더 실측이 가능한 항목(클릭, 색, 대비, 모바일, 게임 런타임)은 실측 결과가 정적 추정을 대체한다. 예: JS가 처리하는 `href="#"` 탭은 정적으로는 '죽은 링크'지만 실제 클릭으로 동작이 확인되면 제외된다 (`examples/js-handled-links`).
- **보정 기준**: `examples/`의 슬롭 샘플은 웹 ≥80 / 게임 ≥60, 수작업 샘플은 <20을 정적·실측 두 모드 모두에서 유지하도록 테스트(`tests/`)가 강제한다.
